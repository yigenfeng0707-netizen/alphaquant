2实测方法 Methodology

全部指标来自当前会话对本公网服务的真实 curl 采样，未使用缓存与模拟数据。
  1. 入口探测：带浏览器 UA 直连首页，确认 HTTP 200 与 SPA 结构；裸 curl 会被 WAF 拦截（403），因此所有采样统一携带 UA。
  2. 端点发现：从前端主包 index-DOMb_JfP.js 提取真实 API 引用，得到 4 个业务端点：/api/screen、/api/suitability、/api/optimize、/api/backtest/walk-forward。旧验证端点 /api/offline/cases 已不在新版前端引用中。
  3. 采样：对 7 个目标（首页 / health / 4 业务接口 / JS 主包）各连续 5 轮，curl 记录 HTTP 码、DNS/TCP/TLS/TTFB/总耗时、下载量、HTTP 版本、远端 IP；轮间无间隔（连续打流最坏工况）。
  4. 协议层复核：openssl s_client 抓取 TLS 版本与证书链，验证证书有效性。
  5. 判据：失败 = 非 2xx / 连接超时 / DNS 解析失败 / 证书校验失败；共 35 项采样。
三层验证结论（上线闭环）：GitHub Actions 构建 success → 魔搭空间 Running → 公网主页 200 + /health ok:true + 业务接口 JSON 可达，三层全绿，当前服务处于可对外演示状态。

6关键发现与风险 Findings & Risks

  • 发现旧验证端点已下线：早前三层验证使用的 /api/offline/cases 已不在新版前端 JS 引用中；直接访问它返回的是 SPA 首页 HTML（416B）而非 JSON——端到端验证的业务判据需同步升级为新端点。
  • 发现SPA fallback 会「伪装」成功：任意未知路径（如 /nope-404-test、/Health）均返回 200 + index.html。单看 HTTP 码不足以证明 API 存活，验证必须校验 Content-Type: application/json 和 ok:true 响应体。
  • 风险计算型接口冷启动延迟：screen/backtest 首轮 TTFB 2.2s / 1.5s，会直接体现在评委现场首次点击上；建议服务启动后预热。
  • 风险前端主包未分包：2.13MB 单 JS（ECharts 全量内联），总加载 ≈1.9s，弱网更明显；建议 vite 按需分包 + gzip。
  • 观察WAF 前置：裸 curl 403，浏览器 UA 200；现场演示用真实浏览器无影响，但脚本化巡检必须携带 UA（现有 verify_3layer 已内置）。
  • 观察安全基线良好：TLS1.2 ECDHE + OV 证书 + 全链路 HTTPS，无安全不符合项。

建议清单（按优先级）

  • P0 · 一次提交内完成：把验证脚本的业务判据从 /api/offline/cases 更新为 /api/screen + /api/backtest/walk-forward，并增加「响应体必须为 JSON 且 ok:true」校验，避免 SPA fallback 误报成功。
  • P1 · 演示前：启动脚本增加预热（拉起后请求一次 4 个业务接口，再进入 READY），把首轮冷启动延迟从演示现场移除。
  • P2 · 可选优化：前端 vite 按需分包 + 静态资源 gzip，目标总加载 <1s；为 /api/optimize 等重计算加进程内缓存。
  • P3 · 可选加固：升级 TLS1.3；给未知 API 路径返回 404 JSON 而非 SPA HTML，让巡检判据更干净（需后端路由调整）。
